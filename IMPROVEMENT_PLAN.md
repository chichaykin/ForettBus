# План улучшений Forett Shuttle

Дата повторного аудита: 18 сентября 2026. Базовая ревизия: `0a51fac`, ветка `main`.

## Оценка состояния

Проект — компактный функциональный MVP для Android. Реализованы два направления,
расписание Пн–Сб, таймер ближайшего рейса, локальное напоминание за 5 минут,
глобальная светлая/тёмная тема и контакты поддержки. Расписание работает локально.
Добавлены live ETA автобусов 41/77 через Cloudflare Worker и устойчивый статический
fallback. До стабильного релиза остаётся сохранить настройки, расширить проверки
уведомлений и настроить CI/release signing.

Хорошая основа:

- Расписание и notification service выделены из экранов.
- `BusSchedule.now()` использует `Asia/Singapore`.
- Инициализация уведомлений идемпотентна; повторные нажатия при обновлении заблокированы.
- Home защищает восстановление напоминания от устаревшего асинхронного результата.
- Таймер останавливается при уходе с вкладки Home, предусмотрен `dispose`.
- Есть unit-, widget- и integration-тесты.
- Android permissions, receivers и adaptive launcher icon настроены в проекте.

## Результаты проверки

- Проверки Flutter, Worker, integration-тест и установка на Pixel выполняются
  перед коммитом по матрице из `AGENTS.md`.
- CI-конфигурации в проверенных стандартных расположениях не найдены.

Аудит не подтверждает актуальность самих часов отправления относительно расписания
Management Office. Доставка уведомлений при отказе в разрешениях, перезагрузке
и энергосбережении требует отдельной проверки на устройстве: существующие
integration-тесты этих сценариев не покрывают.

## Реализовано — живые ETA городских автобусов

Добавлен защищённый Cloudflare Worker в `worker/` и Flutter-клиент для ETA
маршрутов 41 и 77. Worker проверяет ключ приложения до кэша и запроса к LTA,
хранит LTA AccountKey в secrets и кэширует успешный ответ на 20 секунд.
Приложение передаёт ключ через `--dart-define-from-file`, обновляет данные при
смене направления/возврате из фона и останавливает опрос на скрытой вкладке.
При ошибке сети, Worker или LTA приложение использует зашитое расписание
маршрутов 41/77 и явно помечает строки `Scheduled`; расписание учитывает
будни, субботу, воскресенье и рейсы после полуночи. Инструкции развёртывания,
ротации ключей и ограничения резервного расписания находятся в `README.md`.

## 1. P1 — согласованное и надёжное состояние уведомлений

Основание: `lib/screens/home_screen.dart:20`, `lib/screens/profile_screen.dart:26`,
`lib/main.dart:95`, `lib/notifications.dart:16`.

Home и Profile хранят состояние независимо. `IndexedStack` сохраняет оба экрана,
а восстановление запускается только при их создании. Поэтому отмена напоминания
в Profile не очищает отметку на Home; постановка на Home не обновляет переключатель
Profile. Отключение в Profile также не препятствует новой постановке с Home.
Наличие pending reminder сейчас используется как признак «уведомления включены»,
хотя это разные состояния.

- [ ] Разделить пользовательскую настройку, системные разрешения и активное напоминание.
- [ ] Сохранять пользовательскую настройку; проверять её при постановке напоминания.
- [ ] Обновлять разрешения и pending reminder при возвращении приложения на передний план.
- [ ] Сохранить модель одного напоминания, но явно показывать рейс и направление:

- [x] Разрешить повторную инициализацию после ошибки, сохранив идемпотентность

- [ ] Добавить подменяемый notification backend для тестов; ошибки сопровождать

Критерии готовности:

- Постановка, замена и отмена немедленно отражаются на обеих вкладках.
- Выключение уведомлений отменяет активное напоминание и не допускает тихого
  повторного включения через Home.

  настроек, перезагрузка и режим энергосбережения.

## 2. P1 — предсказуемые настройки и расчёты времени

Основание: `lib/main.dart:37`, `lib/schedule.dart:79`, `lib/schedule.dart:85`,
`test/schedule_test.dart`.

Тема хранится только в памяти. Методы расписания принимают произвольный `DateTime`
и интерпретируют часы в его часовом поясе. Текущий Home передаёт сингапурское время
правильно, но публичный API не гарантирует правило проекта: например, 06:00 UTC
сейчас даёт отправление 06:30 UTC вместо расчёта рейса после 14:00 Singapore.
Существующий тест закрепляет именно такое поведение UTC.

Работы:

- [ ] Сохранять тему; добавить режим «Как в системе» наряду со светлой и тёмной.
- [ ] Приводить входное время к `Asia/Singapore` до определения дня недели и рейса.
      Обновить UTC-тест в соответствии с продуктовым правилом.
- [ ] Ввести подменяемый источник текущего времени, сохранив `BusSchedule.now()`
      источником по умолчанию. Сделать UI-тесты независимыми от времени запуска.
- [x] При сворачивании останавливать UI-таймер, при возврате сразу обновлять время.
- [x] Объединить выбор направления Home и Schedule в рамках текущей сессии.
- [ ] Сохранять последний выбор направления после полного закрытия приложения.

Критерии готовности:

- Тема и направление восстанавливаются после полного закрытия приложения.
- Один момент времени, переданный в UTC или Singapore, даёт один и тот же рейс.
- Есть тесты границ суток/недели, последнего рейса в обоих направлениях,
  каждого перерыва и перехода через момент отправления.
- UI-тесты проверяют смену ближайшего автобуса при смене направления,
  тему на всех вкладках и возврат из фона.

## Порядок реализации и контроль

Рекомендуемые небольшие изменения: (1) общий контроллер и тесты уведомлений;
(2) разрешения и восстановление; (3) настройки и Singapore API;
(4) улучшения расписания и доступности; (5) документация, CI и релиз.
CI можно подготовить раньше, чтобы он проверял остальные изменения.

Перед каждым коммитом выполнить проверки из `AGENTS.md`:

```bash
dart format --output=none --set-exit-if-changed lib test integration_test
flutter analyze
flutter test
flutter test integration_test/app_test.dart -d <device-id> --no-uninstall
flutter build apk --debug
adb -s <device-id> install -r build/app/outputs/flutter-apk/app-debug.apk
adb -s <device-id> shell monkey -p com.forett.shuttle_bus -c android.intent.category.LAUNCHER 1
```

После integration-тестов обязательно собирать обычный debug APK заново,
чтобы не оставить тестовый entrypoint. После изменения UI нужна визуальная
проверка на устройстве; после notification logic — проверка permissions
на реальном Android. Не добавлять generated outputs, ключи и локальные настройки
в Git. В текущем изменении выполнена первая часть этапа 1: NotificationService
публикует активное напоминание, Home и Profile синхронизируют его через общий
notifier, а ошибка инициализации больше не блокирует последующие попытки.
Остальные пункты плана требуют отдельной реализации и проверки.
